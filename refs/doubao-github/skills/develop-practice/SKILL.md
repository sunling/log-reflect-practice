# Develop Practice｜发展实践
## 目标
帮助用户把反复出现的真实线索发展成一个小到不可能失败、可以持续调整的实践实验。
这个 Skill 负责从线索到实践设计的转化，不负责替用户决定该做什么，也不负责监督执行或评判成败。实践是用户生活中的实验，可以调整，也可以放弃。
## 什么时候使用
适合：
- 回看日记或输入后，用户对某个反复出现的线索表示"我想做点什么"；
- 用户说"我想养成一个习惯"；
- 用户说"帮我把这个变成一个实践"；
- 某个线索已经多次出现，且用户明确表达了行动意愿。
不适合：
- 只是记录一条新输入：使用 `capture-input`；
- 只是想回看最近的记录：使用 `review-daily`；
- 用户没有表示愿意行动，只是在思考或观察：继续留在 Daily，不急于实践化；
- 已经明确要写文章或做分享：进入对应写作 Skill。
## 核心原则
### 1. 证据优先
实践必须从日记或输入中反复出现的线索发展来，不是凭空设定的目标。
如果没有证据，提醒用户："这个想法是从哪里来的？我们有记录支持吗？"不要因为用户一时热情就帮着构建一个没有根基的实践。
### 2. 小到不可能失败
实践的具体行动要足够小，小到用户在状态最差的一天也能完成。
- 好的例子："穿好鞋出门走五分钟"
- 不好的例子："每天锻炼"
### 3. 实验心态
实践是实验，不是考验。可以调整，可以放弃，可以发现不适合自己。
禁止使用"坚持""自律""打卡"这类暗示道德评判的词。实践的价值在于提供观察自己的机会，不在于完成率。
### 4. 不替用户决定
不要说"你应该做这个实践"。用户是自己生活的专家，AI 只负责帮助澄清和结构化。
### 5. 不承诺结果
不要说"做了这个就会变好"。实践的效果需要用户自己体验和判断。
## 实践四要素
每个实践必须定义以下四要素，缺一不可：
### 触发条件
什么时候做？要具体到场景，而不是时间频率。
- 好："每天早上刷牙后"
- 不好："每天"
### 具体行动
做什么？要小到不可能失败，描述要可观察、可判断是否完成。
### 记录方式
怎么记录做了没有？要低摩擦，不增加额外负担。
- 打勾、一句话、拍照、在日记里提一句，都可以。
### 回顾周期
多久回看一次？建议两周，不要太短（还没形成体验）也不要太长（忘记了初衷）。
## 定义"为什么"
除了四要素，还要帮助用户澄清：希望通过这个实践获得什么具体的变化？
- 好："我希望在通勤时不再感到焦虑"
- 不好："变得更好"
这个"为什么"是后续回顾时判断实践是否有效的参照。
## Markdown 模板
```md
---
name: {practice-name}-github
created: {YYYY-MM-DD}
status: active
review-cycle: 两周
---
# {实践名称}
## 来源
- 这个线索出现在：{日期与文件路径}
- 反复出现的方式：{简要说明}
## 为什么想做这个
{用户希望获得的具体变化}
## 实践设计
- **触发条件**：{什么时候做}
- **具体行动**：{做什么，小到不可能失败}
- **记录方式**：{怎么记录}
- **回顾周期**：{多久回看一次}
## 这是一个实验
可以调整，可以放弃。下次回顾时问自己：
- 这个实践在我的生活中实际发生了吗？
- 它带来了什么变化？（哪怕很小）
- 要不要调整、继续，还是结束？
```
## 质量自测自评
在最终创建实践文档前，必须完成以下自测：
- [ ] 这个实践是否有来自日记或输入的证据支持？
- [ ] 触发条件是否具体到场景？
- [ ] 具体行动是否小到状态最差也能完成？
- [ ] 记录方式是否低摩擦？
- [ ] 是否避免了"坚持""自律"等评判性语言？
- [ ] 是否没有承诺"做了就会变好"？
- [ ] 是否明确了这是一个可调整、可放弃的实验？
## 存储与更新
所有实践归档在：
```text
practices/{practice-name}.md
```
- 文件名使用英文连字符格式，不使用空格（例如 `commute-no-phone.md`）；
- 后续更新实践（添加回顾记录、调整内容）时，覆盖更新已有文件，不创建新文件；
- 实践结束时，将 frontmatter 中的 `status` 改为 `ended`，并在文档末尾记录结束原因和收获。
## GitHub 执行与存储（重要）

在 AI 对话环境中，本地文件系统通常是临时的，因此所有的长期记录都必须通过 GitHub API（或挂载的 GitHub 插件）持久化到目标仓库（默认 `sunling/sunling-os`，或以用户指定的仓库为准）中。

执行步骤：
1. **确认仓库与路径**：目标仓库为 `sunling/sunling-os`。确定文件在该仓库中的相对路径，例如 `daily/inputs/{YYYY}/{YYYYMM}/{YYYYMMDD}-xxx.md`。
2. **检查文件状态**：使用读取工具判断该路径下是否已存在文件。
3. **提交变更**：
   - 如果文件不存在，发起新建文件的 API 调用。
   - 如果文件已存在且需追加，先获取原文件内容（及 SHA 摘要），追加内容后更新。
4. **规范 Commit Message**：使用类似 `feat: add daily input {关键字}` 的格式。
5. **对话返回**：向用户简洁回复“已成功提交到 GitHub: {文件路径}”，不要在对话中打印完整的日记内容。
## 执行反馈
创建后简要说明：
1. 新实践文件路径；
2. 实践的四要素和"为什么"；
3. 提醒用户这是一个实验，下次回顾时间；
4. 若线索证据不足，说明还需要什么确认。
