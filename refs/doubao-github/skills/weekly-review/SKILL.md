# Weekly Review｜回看、追问与发现方向

## 目标

把分散在 Daily 中的生活与输入重新带回来，形成一份可追溯的回看档案。帮助使用者看见自己的注意力、回答问题，并发现少量可能的输出或 Practice 方向。

每次运行至少完成：

```text
读取 Journal 与 Input
→ 识别有证据的 pattern、连接与变化
→ 提出 1–3 个问题
→ 保存 Weekly Review
→ 在对话中继续
```

Weekly Review 到发现方向为止，不在同一流程中起草文章。

## 边界

- 只是保存一条新经历或外部输入：分别使用 `capture-journal` 或 `capture-input`；
- 只是推荐陌生资源：使用 `bubble-breaker`；
- 已经选定主题并确认要写文章：使用 `new-article`；
- 不把每周回看强行写成文章，也不因为出现一个想法就创建 Practice；
- 不把旧 Review 当作本周新发生的原始证据。

## 开始前读取

- 根目录 `README.md`、`PROFILE.md` 与 `.agents/ORCHESTRATOR.md`；
- `reviews/README.md`；
- 指定范围内全部 `daily/journal/` 与 `daily/inputs/`；
- 用户提供的补充材料；
- 只有需要确认线索是否已进入真实行动时，才读取少量相关 Practice；
- 只有继续上一次回看时，才读取对应 Review 档案。

不要为了显得全面扫描整个私人仓库。

## 时间范围

- 用户指定日期范围时严格遵循；
- 用户说“最近七天”“过去一周”或定时任务未指定范围时，默认包含今天并向前回看 7 个日历日；
- 日期优先使用 `PROFILE.md` 中的时区；未填写时使用执行环境的本地日期，只有日期边界仍有歧义时才询问；
- 范围跨月或跨年时检查相邻年月目录；
- 依据文件名、frontmatter 和正文日期确认材料归属，不只看修改时间。

## 第一阶段：回看并存档

### 1. 阅读两类 Daily

完整检查范围内的 Journal 与 Input。即使其中一类没有记录，也要诚实说明，不用另一类假装补齐。

### 2. 以记录为证据

重点辨认：

- 反复出现的问题、场景、感受、词语或判断；
- 外部输入与生活处境发生的真实连接；
- 前后矛盾、理解变化和仍未完成之处；
- 已经发生的行动与反馈，以及仍只是想法的计划；
- 可能值得继续输出或发展为 Practice 的方向。

每个判断都指向日期与仓库相对路径。不能从几条短期记录推断稳定人格、心理诊断或长期命运。

### 3. 提出少量问题

提出 1–3 个真正由本周材料长出来的问题。问题用于帮助使用者继续看见，而不是暗示标准答案、制造行动压力或强迫积极解释。

### 4. 保存 Review

默认路径：

```text
reviews/{YYYY}/{YYYYMM}/{开始日期}-{结束日期}-{关键词}.md
```

文件名中的两个日期都使用 `YYYYMMDD`：前者是回看范围的开始日期，后者是结束日期；年月目录按结束日期归档。`关键词` 从本次最核心且有证据的线索中提取，使用一个简短、具体、便于识别的词或短语，一般不超过 12 个中英文字符；去掉 `/`、`\` 和换行等不适合文件名的字符，不使用“weekly-review”“回看”“总结”等泛称。例如：

```text
reviews/2026/202608/20260817-20260823-产出焦虑.md
```

创建新文件前，先在结束日期对应的月份目录中查找文件名以 `{开始日期}-{结束日期}-` 开头的 Review。已有 1 份时更新原文件并保留原文件名；已有多份时停止并请用户确认，不因后续判断或关键词变化创建重复版本。执行日期继续记录在 frontmatter 的 `date` 字段中。

最小结构：

```markdown
---
date: YYYY-MM-DD
period: YYYY-MM-DD to YYYY-MM-DD
type: weekly-review
---

# YYYY-MM-DD—YYYY-MM-DD｜Weekly Review

## 回看范围

## 本周出现的线索

## 值得注意的连接与变化

## 想继续问的问题

## 可能发展的方向
```

只保留有真实材料的部分。“可能发展的方向”可以为空或明确写“本次没有需要发展成输出或 Practice 的方向”。

### 5. 返回对话

保存成功后，在对话中简洁返回：

1. 回看范围；
2. 2–4 条最值得注意的 pattern、连接或变化；
3. 1–3 个问题；
4. 0–2 个可能的输出或 Practice 方向；
5. Review 档案路径。

不要同时生成一篇文章。

## 第二阶段：继续回应

当使用者回答回看中的问题时：

1. 读取对应 Review；
2. 只整理本轮真实回答，不替使用者补结论；
3. 追加 `## 后续回应`，记录回应日期与内容；
4. 根据新材料重新判断是否存在值得输出或发展 Practice 的方向；
5. 更新原 Review，不创建新文件。

## 输出方向的去向

- Weekly Review 可以根据本周反复出现的注意力、真实行动和输入连接，提出 0–2 个候选输出方向；
- 候选方向不是写作任务，也不代表每周必须输出；
- 只有使用者选择一个主题并明确想继续写时，才交给 `new-article`；
- `new-article` 负责召回相关素材、逐个追问和整理文章草稿；Weekly Review 本身不生成文章。

## 与 Practice 的关系

Weekly Review 是回看档案，不等于 Practice。只有线索已经反复出现、发生行动或获得反馈，并且使用者确认要持续推进时，才交给 `develop-practice`。

## 隐私与事实边界

- 区分用户经历、外部来源表达和 AI 推测；
- 不编造事件、时间、人物、原话、反馈、动机或情绪结论；
- 涉及身体、医疗、关系、工作和第三方经历时，遵循 `PROFILE.md`；
- 方向可能进入公开表达时，单独检查姓名、身份、住址、工作、身体和第三方可识别信息；
- 不确定的事实保留不确定性或列为待确认项。

## 完成检查

- 是否同时检查了 Journal 与 Input，并说明缺少的类别？
- 是否使用了正确的日期范围？
- 每个 pattern 是否有具体日期与路径支撑？
- 是否提出了少量、开放且不诱导的问题？
- 是否已经保存或更新 Review，而不是写入 Daily？
- 是否只提出候选方向，没有在 Weekly Review 内生成文章？
- 是否没有从孤立记录创建 Practice？

## GitHub 执行与存储

AI 对话环境中的本地文件通常是临时的，Weekly Review 必须通过 GitHub API（或已挂载的 GitHub 插件）读取材料并写回配置的目标仓库。

### 真实工具调用红线

- 开始任何 GitHub 操作前，先确认当前运行环境的真实工具列表中存在 GitHub 读取工具；需要保存时还必须存在 GitHub 写入工具。提示词里出现了“GitHub MCP”、工具名称或调用参数，不等于工具真实可用。
- GitHub 操作只能通过运行环境提供的真实 MCP / 插件工具调用完成。严禁使用 bash、shell、终端、`echo`、`printf`、`curl`、`wget`、Python、JavaScript，或在对话中打印 JSON / 代码来模拟工具调用。
- `echo` 出一段请求、展示 API 参数、生成 commit message 或声称“即将调用”，都不代表执行成功，也不能作为读取或写入的证据。
- 如果当前只能使用 bash，找不到真实 GitHub 工具，或写入工具不可用，立即停止，不得反复自我纠正或形成调用循环。明确回复 `GITHUB_TOOL_UNAVAILABLE`，说明尚未写入，并保留目标路径和待写入内容。
- 如果只有读取权限而没有写入工具，允许读取，但必须明确说明当前为只读状态，不能声称已经保存。
- 真实工具调用失败时，按下方错误处理执行；不得改用 shell 模拟，也不得通过不断更换调用格式无限重试。

### 仓库与分支校验

目标仓库：`YOUR_GITHUB_USERNAME/YOUR_REPOSITORY`

- 安装此 Skill 时，先把占位符替换成用户自己的 `owner/repository`；仍有占位符时，读写前必须询问，不能猜测。
- 配置后的完整仓库名是唯一事实来源。每次 GitHub 调用都必须使用它，不得从模板作者、历史对话或其他项目推断仓库，也不得在失败后改投另一个仓库。
- 不要把默认分支写死为 `main`。优先省略 `ref` / `branch`；工具要求显式分支时，先读取仓库信息中的 `default_branch`，本次回看的所有读取和写入使用同一分支。
- 开始回看前，先验证仓库完整名称、可访问性与默认分支。仓库或分支返回 `404` 时停止，不能据此判断“最近七天没有记录”。

### Review 存档

1. 在已验证的仓库和默认分支中读取目标日期范围内的 Journal 与 Input；只有仓库与分支确认可访问后，相关年月目录的 `404` 才表示该目录没有记录。
2. 使用 `reviews/{YYYY}/{YYYYMM}/{开始日期}-{结束日期}-{关键词}.md`，并按结束日期确定年月目录。
3. 创建前先查找文件名以 `{开始日期}-{结束日期}-` 开头的 Review：1 份则完整读取原文与当前 SHA 后更新，0 份才创建，多份则停止并请用户确认。
4. 更新原文件时保留原文件名、已有分析与后续回应，不覆盖无关内容。
5. Review 是定时回看的默认产物，无需每周重复询问是否存档。
6. 使用清楚的 commit message，例如 `Add weekly review: YYYY-MM-DD to YYYY-MM-DD` 或 `Update weekly review: YYYY-MM-DD to YYYY-MM-DD`。
7. 只有写入接口明确成功，并返回 commit SHA、commit URL 或等价成功结果后，才可以说“已成功保存”；若结果含糊，重新读取目标路径确认。

### 后续回应与输出方向

- 用户回答问题时，读取最新文件与 SHA，更新同一 Review。
- 用户选择一个主题并确认要写时，改用 `new-article`；Weekly Review 不创建文章文件。
- 多文件写入时逐项确认；若只有部分成功，必须报告具体成功与失败的文件，不得笼统说“全部完成”。

### 错误处理与真实反馈

- 仓库或分支 `404`：停止，请用户核对仓库名、GitHub 插件连接及目标仓库授权；Private 仓库尤其需要明确授权。
- 写入 `403` / `404`：明确说明“Review 尚未写入 GitHub”，不得尝试其他仓库或声称成功。
- SHA 过期或写入冲突：重新读取最新文件，合并本轮内容后最多重试一次；仍失败则停止。
- 当前环境不能写入时，输出 Review 的目标路径与完整待写入内容，明确说明没有持久化。
- 任何失败都不得提交到模板仓库、作者仓库或历史对话中的其他仓库。
