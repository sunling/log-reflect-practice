# Capture Input｜捕获碎片输入
## 目标
先把真实输入保存下来，不因为分类、提炼或输出压力而丢失当时的触动。
默认写入：
```text
daily/inputs/{YYYY}/{YYYYMM}/{YYYYMMDD}-{关键词}.md
```
`capture-input` 只负责捕获和轻量整理，不负责一次性生成文章、建立复杂项目或替用户得出成熟结论。
知识、智识和智慧可以作为回看一条输入的视角，但不是每条笔记都必须完成的固定栏目：
- 我接触到的内容是什么；
- 它为什么在此刻触动我；
- 它跟我的经历、判断或相信的东西有什么关系；
- 它是否可能影响行动、选择或某个 Practice。
## 边界
- 已明确要写完整文章或分享稿：使用对应写作 Skill；
- 已明确要设计工作坊、咨询材料或社群活动：进入对应 Practice。
## 存储与命名
```text
daily/inputs/{YYYY}/{YYYYMM}/
```
示例：
```text
daily/inputs/2026/202607/20260712-学习与炼化.md
```
规则：
- 需要确定日期时，优先读取 `PROFILE.md` 中的时区；未填写时使用当前执行环境的本地日期，若相对日期仍有歧义再询问；
- 年月目录不存在时安全创建；
- 文件名只保留日期和关键词，不加入来源、平台或输入类型；
- 关键词概括这条输入未来最值得重新找到的内容，不使用空格、斜杠或无意义的版本词；
- 同日同一输入已有文件时，优先更新原文件，不创建 `v2` 或 `final`；
- 同日出现不同输入但关键词重名时，进一步具体化关键词；
- 不向 `daily/inputs/_legacy/` 写入新内容。
来源不是必填信息。只有原始材料明确提供了书名、节目、平台、作者或对话对象等外部来源时，才在 frontmatter 中增加 `source`。来源不明确时直接省略，不写"其他"，也不要猜测。
## GitHub 执行与存储（重要）

在 AI 对话环境中，本地文件系统通常是临时的，因此长期记录必须通过 GitHub API（或已挂载的 GitHub 插件）持久化到配置的目标仓库。

### 仓库配置是唯一事实来源

目标仓库：`YOUR_GITHUB_USERNAME/YOUR_REPOSITORY`

- 安装此 Skill 时，先把上面的占位符替换成用户自己的 `owner/repository`。
- 如果占位符仍未替换，读写前必须询问用户，不能猜测。
- 配置完成后，必须在每一次 GitHub 调用中使用这个完整仓库名。不要从当前材料的链接、模板作者、安装者、历史对话或其他相关项目推断仓库，也不要在失败后改投另一个仓库。
- 不要假定默认分支一定叫 `main`。优先省略 `ref` / `branch`，让 GitHub 使用仓库的默认分支；如果工具要求显式分支，先读取仓库信息中的 `default_branch`，后续所有读取和写入都使用同一分支。

### 写入前校验

本轮第一次访问 GitHub 时，先读取目标仓库的基本信息：

1. 确认返回的完整仓库名与配置完全一致；
2. 确认仓库可访问，并取得真实的默认分支；
3. 只有仓库校验成功后，才检查或创建记录文件。

仓库信息或默认分支返回 `404` 时，不代表记录文件不存在。此时必须停止写入，并请用户检查：

- `owner/repository` 是否拼写正确；
- GitHub 插件是否已经连接；
- 插件是否被授权访问这个仓库，尤其是 Private 仓库；
- 授权范围是否包含内容读写权限。

不要把错误的仓库或分支当成空仓库继续创建文件。

### 创建或更新文件

1. 按 `daily/inputs/{YYYY}/{YYYYMM}/{YYYYMMDD}-{关键词}.md` 确定仓库相对路径。
2. 在已验证的目标仓库和默认分支中读取该路径：
   - 文件存在：获取完整原文和当前 SHA，在原内容基础上追加或更新；
   - 只有在仓库和分支已经验证成功、且目标文件本身返回不存在时，才把它视为新文件。
3. 提交变更：
   - 新文件使用创建文件接口；
   - 已有文件使用更新文件接口，并携带刚读取到的 SHA；
   - 所有调用都显式传入已配置的完整仓库名。
4. Commit Message 使用类似 `feat: add daily input {关键词}`；更新已有记录时可使用 `docs: update daily input {关键词}`。
5. 只有 GitHub 写入调用明确成功，并返回 commit SHA、commit URL 或等价的成功结果后，才能说“已成功提交”。如果工具只返回含糊状态，应重新读取目标路径确认内容已经存在。

### 错误处理与真实反馈

- **目标文件读取 404**：只有仓库和默认分支已验证成功时，才按新文件处理。
- **仓库或分支 404**：停止，不尝试其他仓库或猜测 `main`、`master`。
- **写入返回 403 / 404**：视为授权、仓库或分支问题；明确告诉用户“尚未写入 GitHub”，并指出需要检查的配置，不得声称提交成功。
- **写入冲突或 SHA 过期**：重新读取目标文件，基于最新内容合并后最多重试一次；仍失败则停止，避免覆盖或重复记录。
- **当前环境没有写入能力**：保留目标路径和完整待写入 Markdown，明确说明需要手动保存或补充 GitHub 授权。
- 任何失败都不得转而提交到模板仓库、作者仓库或历史对话中的其他仓库。

成功时简洁回复：

```text
已成功提交到 GitHub：{owner/repository}/{文件路径}
Commit：{commit SHA 或 URL}
```

失败时必须明确使用“未提交”或“尚未写入”，不要只说“处理完成”。

## 整理原则
### 1. 始终保留真实输入
每条笔记至少保留：
- 输入是什么；
- 为什么这一刻值得留下；
- 用户的原始表达。
可以清理明显识别错误、断句和无信息噪音，但**绝对不要**把原始表达改写成成熟文章，更**不可以省略**“我的原始笔记”模块。
### 2. 有内容时再展开
下面这些部分只有材料真实存在时才出现，不为了模板完整而补空话：
- 必要的来源或概念背景；
- 与当下生活、写作、工作坊、咨询、关系或工作的连接；
- 它呼应、挑战或改变了什么判断；
- 仍然不确定的问题；
- 一个可能的行动或 Practice 去向。
不知道时少写，不编造作者、嘉宾、数据、链接、经历、动机和结论。
### 3. 不强迫行动化
一条输入可以只被保存，不必立刻变成待办、文章或 Practice。
只有在用户已经表达真实意愿时，才记录：
- 继续观察的问题；
- 可以尝试的一个小行动；
- 已经准备进入的 Practice。
不要同时维护"后续行动"和"可能的下一步"两套重复栏目。
### 4. 不自动制造下游文件
除非用户明确要求，不自动创建文章、分享稿、工作坊、咨询材料或多个衍生文件。
判断可以是：
- 仍在生活和思考中发生 → 留在 Daily；
- 已准备通过写作、社群、工作坊或咨询接受真实反馈 → 进入对应 Practice；
- 出现反复使用的 AI 工作流 → 考虑更新或新建 Skill；
- 最有价值的是一次选择、对话或实验 → 直接行动，不继续生成文件。
## Markdown 模板
根据材料使用最小版本或展开版本。
### 最小版本
```md
---
title: "{标题}"
date: {YYYY-MM-DD}
tags:
  - {1–3 个标签}
---
## 输入是什么
{必要的内容、观点或背景}
## 为什么此刻想留下
{用户当下的触动；信息不足时保留原始提问或观察}
---
## 我的原始笔记
> {用户原话}
（注意：必须严格输出此 `## 我的原始笔记` 栏目，并一字不差地保留用户的最初输入，不要省略！）
```
若原始材料明确提供了外部来源，可在 frontmatter 中增加：
```yaml
source: "{明确的书名、节目、平台、作者或其他来源}"
```
### 有真实连接时可增加
```md
## 我的思考与关联
{它跟经历、判断、关系、工作或 Practice 的真实连接}
## 仍在想的问题
- {没有答案也可以保留}
## 可能的行动或去向
- {只写一个真实存在的行动、Practice 或"继续留在 Daily"}
```
不要保留空栏目，也不要用"暂无"填满模板。
## 执行反馈
创建后简要说明：
1. 新文件路径；
2. 这条输入为什么值得留下；
3. 若存在，最重要的一条个人连接或真实行动；
4. 若有必要，说明哪些事实或理解仍未确认。
