# Write Weekly Article｜用七天材料写一篇周记

## 目标

把过去一周已经留在 GitHub 仓库中的 Journal 和 Input 重新带回来，整理成一篇可继续修改、默认给自己看的周记文章。

周记不是七天流水账或任务汇报，也不要求每周都有一个主题。它可以留下真实场景、进入注意力的东西、反复出现的问题和暂时没有答案的部分。

## 安装前配置

目标仓库：

```text
YOUR_GITHUB_USERNAME/YOUR_REPOSITORY
```

安装本 Skill 时先替换为用户自己的仓库。占位符未替换时，读取或写入前必须询问，不能猜测目标仓库。

## 边界

- 只回看线索、不生成文章：使用 `review-daily-entries`；
- 保存一条新经历或输入：使用 `capture-journal` 或 `capture-input`；
- 不因为生成一篇周记就自动创建 Practice、公开文章或其他文件；
- 默认只在对话中返回文章。只有用户明确要求保存时，才通过 GitHub API 提交；
- 默认不发布。准备公开时再检查隐私、第三方许可和表达边界。

## 时间范围

- 用户指定日期范围时严格遵循；
- 用户说“过去一周”“最近七天”或没有说明范围时，默认包含今天并向前回看 7 个日历日；
- 优先读取目标仓库 `PROFILE.md` 中的时区；未填写且日期边界会影响范围时先询问；
- 范围跨月或跨年时检查相邻年月目录；
- 依据文件名、frontmatter 和正文日期确认材料归属，不只看 commit 时间；
- 若范围中包含以前生成的周记，默认排除，避免把整理稿误当成新发生的原始材料。

## 从 GitHub 读取

通过 GitHub API 或已授权插件读取：

```text
daily/journal/{YYYY}/{YYYYMM}/
daily/inputs/{YYYY}/{YYYYMM}/
```

执行：

1. 确认仓库和默认分支；
2. 列出时间范围涉及的年份、月份目录；
3. 按文件名日期前缀筛选目标文件；
4. 获取所有符合范围的 Journal 和 Input 正文；
5. 完整阅读后再写，不只根据文件名、搜索摘要或 commit message 猜测内容；
6. 只在需要核对某条记录时补读直接相关的少量文件，不扩大到整段历史。

## 写作前整理

先在内部整理：

- 本周真实发生的场景、行动和身体感受；
- 进入注意力的书、文章、播客、对话、观察或问题；
- 反复出现的词语、张力、矛盾和未完成状态；
- Journal 与 Input 之间有证据的连接；
- 值得保留的用户原句；
- 没有发生的计划，以及隐私或第三方风险。

从中辨认 2–4 条候选线索，默认选择证据最充分的一条直接写草稿。只有选择不同会明显改变文章且材料无法判断时，才一次问一个问题；用户要求直接写时不要阻塞。

## 写作方式

保留第一人称、具体场景、生活颗粒、真实触动、犹豫和未完成感。允许没有连接的生活片段并列存在。

避免：

- 按星期一到星期日写流水账；
- 写成工作汇报、任务清单或效率复盘；
- 从短期记录推断人格或心理结论；
- 强行升华或制造不存在的因果；
- 把外部输入摘要写成主要正文；
- 大段复制书、文章、播客等受版权保护的原文。

正文通常为 1000–2000 字。材料较少时宁可更短，也不要凑字数。标题优先来自具体场景、反复问题或用户原句；没有自然标题时使用 `{开始日期}—{结束日期}｜周记`。

## 输出与保存

默认在对话中返回标题、正文、日期范围和必要的待确认项，不附加每日摘要或分析报告。

用户明确要求保存时：

1. 使用用户指定的仓库相对 `output_path`；
2. 未指定且没有既有写作目录时，先询问，不自动创建 Practice；
3. 同一周期已有草稿时先获取原文件内容和 SHA，再更新原文件，不创建 `v2` 或 `final`；
4. 新建或更新文件后提交到配置的目标仓库；
5. commit message 使用 `feat: add weekly article YYYY-MM-DD`，更新旧稿时相应改为 `docs: update weekly article YYYY-MM-DD`；
6. 回复中提供仓库相对路径和 commit 信息。

新文件没有其他约定时，可使用：

```yaml
---
title: "{文章标题}"
date: YYYY-MM-DD
period: YYYY-MM-DD to YYYY-MM-DD
tags:
  - 周记
---
```

## 隐私与事实

- 区分用户经历、外部来源表达和 AI 推测；
- 不编造事件、人物、原话、反馈、动机或情绪结论；
- 默认文章给本人阅读，不等于默认可以公开；
- 准备分享时检查姓名、关系、工作、住址、身体、医疗和第三方可识别信息；
- 不确定的事实保留不确定性或列为待确认项。

## 完成检查

- 是否读取了正确范围内的 Journal 与 Input？
- 是否诚实说明某一类材料缺失？
- 文章是否由具体记录支撑，并保留用户语气？
- 是否没有为了字数制造内容或连接？
- 是否没有未经要求提交、创建 Practice 或公开发布？

完成后返回文章；若已保存，再简要说明 GitHub 路径、commit、日期范围和待确认的事实或隐私。
