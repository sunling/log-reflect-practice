# Develop Article｜从一个主题到简单文章

## 目标

帮助使用者把已经选定的主题说清楚，而不是替使用者制造一个看起来完整的观点。

```text
选定一个主题
→ 找回相关记录
→ 逐个追问真实行动、个人关联与具体细节
→ 确认最想表达的一条主线
→ 整理成一篇简单文章
```

## 边界

- 还不知道写什么、需要从近期注意力中寻找方向：先使用 `weekly-review`；
- 只是保存一条新经历或外部输入：分别使用 `capture-journal` 或 `capture-input`；
- 不因为 Review 出现候选方向就自动写文章，必须由使用者选择主题并确认继续；
- 不要求每篇文章都公开，不把社交媒体的流行写法当作默认标准；
- 默认只在对话中返回草稿，不自动保存或发布。

## 开始前读取

- 根目录 `PROFILE.md` 与 `.agents/SOUL.md`；
- 使用者选定的主题、Review、Daily 路径或直接提供的材料；
- 只有为了找回与主题直接相关的证据时，才读取少量 `daily/journal/`、`daily/inputs/` 或 Practice；
- 使用者已经说明的平台、受众、语气、长度和隐私要求。

不要为了让文章显得丰富而扫描全部私人记录。

## 先判断材料是否足够

起草前至少需要理解：

1. 使用者围绕这个主题实际做过、经历过或观察过什么；
2. 这个主题为什么在此刻与使用者有关；
3. 至少一个能够进入文章的具体场景、动作、对话或细节；
4. 使用者当前的看法、疑问、矛盾或尚未想清楚之处。

如果材料已经回答，不重复提问。缺少关键信息时，每次只问一个最能推进表达的问题，等待回答后再继续。问题应从现有材料长出来，例如：

- 你在这个主题上真正做过哪一件事？当时发生了什么？
- 哪一个具体时刻让你意识到它和自己有关？
- 你的想法和一开始相比有什么变化？
- 有没有一处矛盾、失败或不确定，是你不想在文章里抹平的？
- 你最想让哪一类人读到，或者这篇文章只需要先写给自己？

通常问到已经有一条清楚主线和足够真实细节即可，不为了完成固定题数继续追问。

## 整理文章

- 使用第一人称，保留使用者自己的用词、节奏、犹豫和未完成感；
- 优先从具体场景、真实动作或一个仍在发生的问题进入，不用空泛背景开头；
- 围绕一条主线组织材料，不写成输入摘要、周报或按日期排列的流水账；
- 外部输入负责提供触动和参照，生活经历负责提供文章的真实颗粒；
- 清楚区分外部来源的观点、使用者的判断和 AI 的推测；
- 不补写经历、人物、反馈、动机、情绪或引用；
- 不为了完整强行加入结论、行动建议或积极升华；
- 没有指定平台时，先写一篇平台中立的简单文章；材料少时宁可更短，不凑字数；
- 指定平台后再调整标题、长度、分段和开头，但不自动改成爆款腔或营销文案。

## 返回草稿

默认返回：

1. 一个工作标题；
2. 完整文章草稿；
3. 仍需使用者确认的 0–3 处事实、表达或隐私边界。

草稿之后先继续打磨。只有使用者明确要求并确认目标路径时，才保存文件；没有明确去向时不要自动创建 Writing Practice。除非使用者在当前对话中明确要求且目标无歧义，否则不向任何平台发布。

## GitHub 材料与保存

目标仓库：`YOUR_GITHUB_USERNAME/YOUR_REPOSITORY`

- 使用相关 Daily 或 Review 前，先确认当前环境存在真实可调用的 GitHub 读取工具；没有工具时不要用 shell、`curl`、打印 JSON 或代码模拟读取，可以请使用者直接提供材料；
- 仍有仓库占位符时先询问，不能从模板作者或历史对话猜测目标仓库；
- 只读取与选定主题直接相关的文件，并使用仓库默认分支；
- 默认草稿只返回对话，不需要写入 GitHub；
- 使用者明确要求保存并确认仓库相对路径后，才使用真实 GitHub 写入工具；只有接口返回 commit SHA、commit URL 或等价成功结果，才可以说已经保存；
- 读取或写入失败时明确说明未完成，不改投其他仓库，也不把内容提交到模板仓库。

## 完成检查

- 主题是否由使用者选择，而不是 AI 从 Review 中擅自决定？
- 是否写出了使用者真实做过或经历过的事情？
- 是否说明了主题为什么与使用者有关？
- 是否包含至少一个具体而可核对的细节？
- 是否保留必要的矛盾、不确定和未完成之处？
- 是否没有把外部来源的表达写成使用者自己的观点？
- 是否没有编造经历、情绪、反馈、引用或结论？
- 是否检查了第三方隐私和公开边界？
- 是否只返回或保存了使用者真正要求的结果？
