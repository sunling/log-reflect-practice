# Review Daily｜回看时间轴

## 目标

帮助用户重新进入一段时间里的真实记录，看见正在反复发生的问题、理解和行动，而不是把 Daily 压缩成一份漂亮总结。

这个 Skill 负责发现、连接和判断下一步，不负责直接生成文章、分享稿、工作坊或咨询材料。用户选定真实去向后，再交给对应 Skill 和 Practice。

## 什么时候使用

适合：

- “看看最近一周的输入”；
- “回看这个月的记录”；
- “我最近反复在想什么”；
- “这些笔记之间有什么连接”；
- “有哪些可以整理成分享”；
- “哪些内容值得继续写、做实验或带进工作坊”。

不适合：

- 只是要保存刚刚产生的一条输入：使用 `capture-input`；
- 已经明确要生成文章、分享或其他成品：使用对应的写作 Skill；
- 已经明确要推进某个 Practice：直接进入该 Practice。

## 开始前读取

- 根目录 `README.md`；
- `.agents/ORCHESTRATOR.md`；
- 用户指定时间范围内的 `daily/inputs/`；
- 只有在需要确认生活处境、行动变化或时间线时，才读取必要的 `daily/journal/`；
- 只有在判断内容是否已经进入真实实践时，才读取少量相关 Practice 文件。

不要为了显得全面穷举整个仓库。

## 时间范围

- 用户指定日期范围时严格遵循；
- 用户说“最近一周”时，优先按 `PROFILE.md` 中的时区计算；未填写时使用执行环境的本地日期，向前回看 7 天并包含今天；
- 用户没有说明范围时，默认最近 7 天；
- 时间范围跨月或跨年时，检查相邻年月目录；
- 日期优先依据文件名、frontmatter 和正文时间，不只看 Git 修改时间。

## 回看原则

### 1. 以记录为证据

每个判断都要能指向具体文件、日期或真实行动。不能从几条短期记录推断稳定人格、心理诊断或长期命运。

### 2. 识别反复，不制造主题

重点看：

- 哪些问题、词语、场景或情绪反复出现；
- 哪些输入与生活处境发生了真实连接；
- 哪些地方存在前后矛盾、判断变化或尚未解决的问题；
- 哪些计划已经行动，哪些仍只是想法；
- 哪些内容已经进入某个 Practice，哪些仍适合留在 Daily。

只有真正有证据的连接才保留。不要把无关碎片拼成一个宏大主题。

### 3. 区分四种状态

每个值得注意的方向只需要判断它当前更接近哪一种：

1. **继续留在 Daily**：仍在生活和思考中发生，不急着输出；
2. **继续观察**：已经反复出现，但还缺生活证据、反例或行动；
3. **进入真实 Practice**：已经准备通过持续行动、表达或服务接受真实反馈；
4. **直接行动**：最有价值的下一步不是继续生成文件，而是做一次选择、对话或实验。

不要把每个方向都推向公开输出。

## 输出结构

默认在对话中使用以下结构，不写入仓库：

```md
## 回看范围
- 时间：
- 主要读取：
- 必要补充：

## 最近反复出现的内容
### 1. {问题或方向}
- 证据：{日期与相对路径}
- 现在发生了什么：
- 仍然缺什么：

## 值得注意的连接与变化
- {真正有证据的连接、矛盾或行动变化}

## 当前去向判断
- 继续留在 Daily：
- 继续观察：
- 可能进入的 Practice：
- 更适合直接行动：

## 最值得继续的 1–3 个方向
1. {方向与理由}
```

内容不够时可以更短，不为填满栏目制造判断。

## 与下游 Skill 的交接

用户选定方向后：

- 若它仍只是需要继续观察的问题，保留在 Daily；
- 若它已经准备持续行动和接收反馈，交给 `develop-practice`；
- 若仓库中另有对应的写作、项目或领域 Skill，先读取其说明再交接；
- 交接时只传递真正相关的来源路径、核心问题和仍待确认的部分，不复制同一份正文到多个位置。

## 写入边界

默认不创建：

- 周报或月度回看文件；
- “智识”“理解”“思考项目”等中间目录；
- 为每个候选方向创建独立草稿；
- 跨 Practice 的统一复盘日志。

只有用户明确要求“把这次回看记录下来”时，才把本次回看作为一条当前日期的输入，按照 `capture-input` 的规范写入 `daily/inputs/{YYYY}/{YYYYMM}/`，并链接主要来源。不要建立专门的 review 目录。

## 隐私与事实边界

- 私人日记、身体、医疗、关系、工作和第三方经历只在帮助用户理解自己时使用；
- 推荐公开表达前，单独标记需要匿名化、授权或删除的细节；
- 不把短期情绪写成长期性格；
- 不把计划写成已经发生；
- 不把 AI 推测写成用户已经确认的判断。

## 完成后的回复

简要说明：

1. 回看的日期范围和主要材料；
2. 识别出的少量反复问题或变化；
3. 最值得继续的 1–3 个方向；
4. 哪些判断仍需要用户确认；
5. 默认没有创建新文件。
