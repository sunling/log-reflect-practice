# Write Weekly Article｜用七天材料写一篇周记

## 目标

把过去一周已经留下的 Journal 和 Input 重新带回来，整理成一篇可继续修改、默认给自己看的周记文章。

周记不是按日期罗列完成事项，也不是强迫每一周都有一个主题。它可以留下这一周真正发生的场景、进入注意力的东西、反复出现的问题，以及暂时没有答案的部分。

## 边界

- 只想知道最近反复出现什么，不需要文章：使用 `review-daily-entries`；
- 只是保存一条新经历或外部输入：分别使用 `capture-journal` 或 `capture-input`；
- 已经明确要把某条线索发展成持续行动：使用 `develop-practice`；
- 不因为生成了一篇周记，就自动创建新的 Practice、公开文章或下游文件；
- 默认不发布。用户明确准备公开时，再单独处理隐私、第三方许可和表达边界。

## 开始前读取

- 根目录 `README.md`、`PROFILE.md`；
- `.agents/SOUL.md` 与 `.agents/ORCHESTRATOR.md`；
- 目标时间范围内的 `daily/journal/` 和 `daily/inputs/`；
- 用户提供的补充材料或指定输出路径；
- 只有用户明确要求保存，且仓库已有写作 Practice 时，才读取该 Practice 的 `README.md`、`mission.md` 或命名约定。

不要为了寻找更漂亮的主题扩大到整段个人历史。需要核对某条记录中的既有 Practice 或外部来源时，只补读直接相关的少量文件。

## 时间范围

- 用户指定日期范围时严格遵循；
- 用户说“过去一周”“最近七天”或没有说明范围时，默认包含今天并向前回看 7 个日历日；
- 日期优先使用 `PROFILE.md` 中的时区；未填写且当前日期边界会影响范围时，先询问；
- 范围跨月或跨年时，检查相邻年月目录；
- 依据文件名、frontmatter 和正文日期确认材料归属，不只看 Git 修改时间；
- 不把以前生成的周记误当作这一周新发生的原始材料。若来源范围中包含既有周记，默认排除，除非用户明确希望比较前后变化。

## 写作前整理

完整阅读范围内符合条件的记录，先在内部整理：

- 这一周真实发生的具体场景、行动和身体感受；
- 进入注意力的书、文章、播客、对话、观察或问题；
- 反复出现的词语、张力、矛盾或未完成状态；
- 日记和输入之间有证据的连接；
- 值得保留的用户原句；
- 哪些计划没有发生，不能写成已经完成；
- 哪些细节涉及隐私、第三方或公开风险。

不要先决定主题，再挑选材料证明它。没有连接的内容可以并列存在，也可以不写进本次周记。

## 选择文章重心

从材料中辨认 2–4 条候选线索，并判断：

- 哪一条最能承载这一周的真实状态；
- 哪些具体场景可以把它写实；
- Journal 与 Input 是否发生了真实连接；
- 哪些问题应该保持开放，而不是被文章过早回答。

默认选择证据最充分的一条主线直接形成草稿，不把选材工作重新推给用户。

只有当两条线索都很重要、选择不同会明显改变整篇文章，而且材料无法判断时，才展示精简候选并一次只问一个问题。用户要求“直接写”时，说明关键假设后继续，不阻塞生成。

## 写作方式

### 保留

- 第一人称与用户原有语言；
- 具体场景、动作、感受、对话背景和时间现场；
- Journal 中的生活颗粒，以及 Input 真正触发的个人回应；
- 犹豫、矛盾、变化和没有想清楚的问题；
- 一两句话一个段落的自然节奏；
- 不整齐但真实的一周。

### 避免

- 按星期一到星期日写成流水账；
- 把周记写成工作汇报、任务清单或效率复盘；
- 从几条记录推断稳定人格、心理诊断或人生阶段；
- 用“这一周我深刻认识到”一类句子强行升华；
- 把外部输入摘要当成主要正文；
- 用 AI 的语言替用户补出动机、感受、因果或结论；
- 为了达到字数重复表达或制造不存在的连接；
- 大段复制书、文章、播客或其他受版权保护的原文。

正文通常为 1000–2000 字。材料较少时宁可更短，也不要凑字数；材料很多时选择真正服务文章的部分，不把全部记录塞进去。

标题尽量来自一个具体场景、反复问题或用户自己的短句。没有自然标题时，可以使用：

```text
{开始日期}—{结束日期}｜周记
```

## 输出与保存

### 默认输出

用户只要求“生成”“写一篇”或“整理成周记”时，直接在对话中返回：

1. 标题；
2. 周记正文；
3. 一句简短说明：使用的日期范围，以及是否存在需要本人确认的事实或隐私。

默认不附加分析报告、每日摘要或候选主题清单。

### 用户明确要求保存

- 用户提供 `output_path` 时，使用该仓库相对路径；
- 仓库已有写作 Practice 和明确命名约定时，遵循现有约定；
- 两者都没有时，先询问希望保存到哪里，不自动创建新的 Practice；
- 写入已有草稿前先完整阅读并更新原文件，不创建 `v2`、`final` 或重复副本；
- 新文件没有其他约定时，可使用以下最小 frontmatter：

```yaml
---
title: "{文章标题}"
date: YYYY-MM-DD
period: YYYY-MM-DD to YYYY-MM-DD
tags:
  - 周记
---
```

日期使用 `PROFILE.md` 中的时区；未填写且日期有歧义时先询问。

## 隐私与事实检查

- 区分用户经历、外部来源表达和 AI 推测；
- 不编造事件、时间、人物、原话、反馈、动机或情绪结论；
- 默认文章给本人阅读，不等于默认可以公开；
- 用户准备分享时，检查姓名、关系、工作、住址、身体、医疗和第三方可识别信息；
- 他人的故事没有明确许可时，不作为公开文章的核心素材；
- 不确定的事实保留不确定性，或在回复中列为待确认项。

## 完成检查

- 是否使用了正确的 7 天或指定日期范围？
- 是否同时检查了 Journal 与 Input，并诚实说明缺少的类别？
- 文章是否由具体记录支撑，而不是通用周总结？
- 是否保留了用户语气、真实细节和未完成感？
- 是否避免把外部输入摘要或任务汇报当成正文？
- 是否没有为了 1000–2000 字制造内容？
- 是否没有自动创建 Practice、衍生文件或公开发布？

## 完成后的回复

未保存时，返回标题、正文、日期范围和必要的待确认项。

已保存时，简短说明：

1. 写入或更新的仓库相对路径；
2. 使用的日期范围；
3. 仍需本人确认的事实、隐私或公开边界。
